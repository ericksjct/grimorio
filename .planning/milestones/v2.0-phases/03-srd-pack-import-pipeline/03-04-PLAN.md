<objective>
Materializar os dois pacotes SRD embutidos (D-01, D-02) a partir da fonte cuja licença o plano 03-02 verificou, com o script de geração commitado para regeneração futura.

Purpose: é o critério 6 da fase — o conteúdo SRD tem de existir como pacote real, no mesmo formato, instalável pelo mesmo pipeline. É também o que torna a Fase 6 (remoção dos 4 JSONs protegidos) possível sem deixar o app vazio.
Output: `scripts/generate-srd-pack.mjs`, `srd-2014-en.json`, `srd-2024-en.json`, `scripts/check-srd-packs.tests.ps1`.

**Nomenclatura (discricionariedade delegada ao planner por D-14):** os arquivos e os `meta.source` usam `srd-2014-en` / `srd-2024-en` — o vocabulário de edição que o app já usa em `SPELL_VERSIONS` e nos nomes de `spells-5E-*.json`. A versão do documento SRD (5.1 / 5.2) vai em `meta.version`. Ponto de atrito evitado: `meta.source` tem `pattern` `^[a-z0-9][a-z0-9-]{0,63}$`, que não aceita ponto — `srd-5.1-en` seria inválido contra o próprio schema.

**Escopo explicitamente fora deste plano:** pré-instalar os pacotes SRD no boot e adicioná-los ao `PRECACHE` do `sw.js`. Isso é SRD-03, Fase 4. Aqui eles só precisam existir como arquivos válidos e instaláveis pelo pipeline.
</objective>

Comentário de cabeçalho: o que o script faz, de onde vêm os dados (URL registrada em `03-SRD-SOURCE.md`, citada literalmente), quando rodar de novo (quando o SRD for atualizado), e a regra D-05 em uma frase.

Estrutura:
- Uma constante `EDITIONS` com duas entradas, cada uma com: `file` (`srd-2014-en.json` / `srd-2024-en.json`), `source` (`srd-2014-en` / `srd-2024-en`), `edition` (`2014` / `2024`), `srdVersion` (`5.1` / `5.2`), `sourceUrl` (a URL do dataset registrada em `03-SRD-SOURCE.md`), e `attribution` (o texto verbatim daquela edição, copiado de `03-SRD-SOURCE.md` — os dois textos são diferentes; se saírem iguais, a extração está errada).
- Uma constante `MODIFICATION_NOTE` com a nota genérica única de D-04 (texto reformatado para JSON e HTML estrutural; conteúdo não alterado), aplicada às duas edições.
- `fetchSource(edition)` — baixa (ou lê de um cache local em `.cache/` fora do git, se o script já tiver baixado) o dataset da `sourceUrl`.
- `toSpell(raw)` — mapeia UM registro da fonte para a forma de `spells[]` do schema. Preenche os obrigatórios (`name`, `level`, `school`, `description`) e os opcionais que a fonte tiver. `name` é o ID estável dentro do pacote: derive um slug em minúsculas com hífens a partir do nome em inglês da magia, e garanta unicidade dentro do pacote (se colidir, sufixe com `-2`, `-3`, seguindo a mesma regra de `freeIdentifier`). `displayName` recebe o nome legível. `description` recebe o HTML da fonte, restrito às tags que a página de docs lista; se a fonte entregar texto puro, envolva parágrafos em `p` — não invente marcação estrutural que a fonte não tinha.
- `buildPack(edition, spells)` — monta `{ meta, spells }` com `meta.source`, `meta.name` (ex.: `SRD 5.1 (EN)`), `meta.version` = `srdVersion`, `meta.author` (a entidade que publica o SRD, conforme registrado em `03-SRD-SOURCE.md`), `meta.lang` = `en`, `meta.edition`, `meta.spellCount` = número de magias, e `meta.license` com `id`, `attribution` da edição, `modifications` = `MODIFICATION_NOTE`, e `url` da licença.
- `main()` — para cada edição: busca, mapeia, monta, e ANTES de gravar valida o resultado contra `pack.schema.json` carregando o próprio arquivo de schema e aplicando as mesmas regras de tipo/obrigatoriedade (não instale uma dependência de validação de schema; o projeto não tem gerenciador de pacotes em uso no runtime e a validação necessária aqui é a mesma tabela do validador). Se falhar, aborte com mensagem apontando o campo — nunca grave um pacote inválido. Grava com `JSON.stringify(pack, null, 2)` mais quebra de linha final.
- Saída no console: uma linha por edição com o arquivo escrito e a contagem de magias.

Não adicione dependências. `fetch` e `node:fs/promises` bastam.
