## Summary

The core wiring of the phase is correct. `uiLang` is genuinely independent state
(`index.html:412`), the `hifi-spells-source-changed` handler no longer writes a
language setter, `langOfVersionKey` is gone with zero dangling references, and
the `HifiLangToggle` rewrite does what D-09 asked: two states, always enabled, no
version-registry reads. `window.__setUiLang` has no staleness problem — it closes
over a stable React setter, is declared before the `if (!character) return null`
early return so its effect always runs, and both call sites guard with
`window.__setUiLang &&`. All 24 source-assertion scripts pass (`scripts/run-tests.ps1`).

Four of the six focus items came back clean and I want that on the record, because
they were the plausible failure modes:

- **Print/share signature split (focus 4):** every live call site is correct.
  `hifiPrintPrepared(preparedSpells, uiLang, versionLang, showToast, {...})` at
  `v10-hifi.jsx:1384` and `:2567` matches `(spells, uiLang, versionLang, show, opts)`;
  `hifiCopyLink(s, lang, show)` was not re-ordered and its two call sites still pass
  the UI language; `HifiPrintCard` receives both props by name. No argument-order defects.
- **`lang` per region (focus 3):** all 5 `dangerouslySetInnerHTML` sinks carry
  `lang={hifiHtmlLang(versionLang)}` on the same element, and the values are right
  (`'pt-br'`/`'en'`). Registry `lang` is normalized to exactly `'ptbr'|'en'` at
  `spells-data-loader.jsx:71`, so `hifiHtmlLang`'s strict `=== 'ptbr'` is safe for
  every value that reaches it from the version registry. Gaps are in the *unmarked*
  regions, not in wrong values — see WR-04/WR-05.
- **Dead code removal (focus 5):** `remapClassFilter` is genuinely gone, declaration
  and call site, with a negative assertion guarding it. (Its removal is nonetheless
  the source of the one Critical below.)
- **Weakened tests (focus 6):** the `check-edition-compare.tests.ps1` CR-02
  replacement is an *inversion*, not a weakening. The real CR-02 invariant — one
  shared `hifiSiblingVersion()` that owns the corpus preference (`v.corpus === cur.corpus`),
  called by `useEditionCompare` — is still asserted verbatim. The toggle-side assertion
  went from "must call it twice" to "must not call it, and must not touch `versions` at
  all", which is *stronger* than the old narrow `versions.find(v => v.lang === ...)` ban.

What is not clean is the *consequence* of the D-04 dead-code removal, one
re-coupling of UI preference back into content selection that the phase was

## Critical Issues

### CR-01: Class filter silently orphaned when the pack language changes — spell list goes empty with no explanation

**File:** `v10-hifi.jsx:863-874` (removed remap), `v10-hifi.jsx:758` (filter value source), `v10-hifi.jsx:885-895` (character auto-filter)

**Issue:** D-04 justified deleting `remapClassFilter` with "o `Set` passa a guardar
sempre o valor do pack, não há mais o que remapear na troca". That premise is false.
The Set holds the value of the pack that was active **when the filter was set**, not
the one active now. Trace it:

1. `spells-data-loader.jsx:343` writes `classes: versionLang === 'ptbr' ? classesPt : classesEn`
   — so `s.classes` is `['mago', ...]` on a PT pack and `['wizard', ...]` on an EN pack.
2. `hifiFilterConfig().class.get = s => (s.classes || [])` (`v10-hifi.jsx:758`) and
   `hifiFilterValues('class', allSpells, versionLang)` both surface those raw pack values,
   and `toggleFilter` stores the raw value in `filters.class`.
3. The user selects "Mago" on a PT pack → `filters.class = Set{'mago'}`.
4. The user switches to an EN pack. The version-change effect (`:867-873`) now does
   **only** `setSelectedIdx(null)`. `filters` is untouched.
5. The filter engine intersects `Set{'mago'}` with `['wizard', ...]` → **zero matches**.
   The list empties, and because the pill list is rebuilt from the new pack's values,
   *every class chip renders inactive* while the chip counter still reads `1`. The user
   sees an empty grimoire with no filter visibly applied.

The character auto-filter is broken by the same removal and cannot rescue it: it
computes `classSet` through `CLASS_PT` gated on `versionLang` (`:888-889`) but its
effect depends on `[charClassSig]` only — it does not re-run on a version change.
Before this phase `remapClassFilter` was the single mechanism that repaired both;
nothing replaced it.

This is a regression against working behavior, and it is exactly the failure shape
the project forbids elsewhere ("referência que não resolve deve ser sinalizada,
nunca sumir em silêncio", `04.1-CONTEXT.md` §Deferred). It also contradicts plan 05's
own stated pattern — conc/rit were canonicalized to `'yes'`/`'no'` precisely so they
would "survive an interface-language switch while active", but the class filter, which
survives *pack*-language switches, was left holding a language-bound value.

**Fix:** Store the canonical (EN) class key in the Set and keep `hifiClassFilterLabel`
as the render-time translation — the same shape already used for conc/rit and school.
`adaptSpell` already writes `classesEn` on every spell (`spells-data-loader.jsx:345`),
so this costs nothing:

```jsx
// v10-hifi.jsx:758 — filter on the canonical key, never the localized value.
class:  { label: tt(lang, 'spell.class'), base: true, get: s => (s.classesEn || s.classes || []) },
```

`hifiClassFilterLabel(value, uiLang)` already turns `'wizard'` into `Mago`/`Wizard`, so
the visible chips are unchanged. The character auto-filter then simplifies to the
canonical key and stops depending on `versionLang` entirely:

```jsx
// v10-hifi.jsx:888-889
const classSet = new Set(cls.map(c => String(c.class).toLowerCase()));
```

If the canonicalization is judged too broad for this phase, the minimum fix is to
restore the remap in the version-change effect (`:867`) — but that leaves the
character auto-filter still stale, so it is the worse of the two.

Add a negative assertion to `scripts/check-filter-lang-vocabulary.tests.ps1` pinning
that the class filter `get:` does not read the language-bound `s.classes`.

## Warnings

### WR-01: Initial version is still chosen from the UI-language preference — the coupling the phase removed, running in reverse

**File:** `index.html:404-406`

**Issue:** `defaultVersionKeyForLang(initial.lang || detectLang())`. Before this phase
`initial.lang` *was* the pack language (it was written from `langOfVersionKey`), so
feeding it into version resolution was self-consistent. After this phase `initial.lang`
is `prefs.lang`, i.e. the user's **interface** preference. D-12 sanctions the browser
language (`detectLang()`) influencing the initial version; it does not sanction the UI
preference doing so.

Reachable: the persistence effect (`index.html:475-479`) can write `versionKey: ''`
when the loader has not resolved a version yet while still writing `lang: uiLang`.
On the next boot `initial.versionKey` is falsy and `initial.lang` decides the pack.
A user who set the interface to PT specifically so they could read EN packs then gets a
PT pack forced on them — the exact scenario the phase exists to prevent.

**Fix:**

```js
// index.html:406
|| defaultVersionKeyForLang(detectLang());
```

`detectLang()` is the browser signal D-12 named; drop the `initial.lang` step.

### WR-02: `uiLang` boot value is never normalized, so `<html lang>` and `og:locale` can disagree with the rendered text

**File:** `index.html:412-414`, `index.html:501-503`

**Issue:** `React.useState(initial.lang || detectLang())` takes `prefs.lang` from
localStorage raw. D-19 waived a validation guard on the grounds that `normLang`
collapses anything to `'ptbr'|'en'` — true for every *dictionary* lookup, but the two
a11y attributes bypass `normLang` entirely and use a strict comparison:

```js
document.documentElement.setAttribute('lang', uiLang === 'ptbr' ? 'pt-br' : 'en');
```

A stored value of `'pt'` or `'pt-BR'` renders a fully Portuguese UI (`normLang` →
`'ptbr'`) inside `<html lang="en">` with `og:locale=en_US`. That is a WCAG 3.1.1
failure and it mislabels every screen reader announcement on the page. The same hole
exists in `hifiHtmlLang` (`v10-hifi.jsx:12`), which is safe today only because
`spells-data-loader.jsx:71` happens to normalize registry entries.

**Fix:** normalize once at the source, where the phase already routes the setter:

```js
const [uiLang, setUiLang] = React.useState(
  normLang(initial.lang || detectLang())
);
```

Zero new guards, no new code path — the same `normLang` that `window.__setUiLang`
already uses. Optionally make `hifiHtmlLang` route through `window.normLang` too, so
the attribute value can never disagree with the text.

### WR-03: Desktop level filter shows the raw Portuguese literal `truque` in an English interface

**File:** `v10-hifi.jsx:756` (value), `v10-hifi.jsx:1262-1266` (desktop, no `formatValue`), `v10-hifi.jsx:2480` (mobile, translated)

**Issue:** The `level` filter's canonical values are `['truque','1',...,'9']`. Mobile
translates the sentinel inline:

```jsx
{v === 'truque' ? (tt(lang, 'spell.cantrip')) : v}
```

Desktop's `filterCats` level entry is the only one of the three without a `formatValue`,
so `FilterChipDropdown` renders `formatValue = v => v` and the dropdown reads
"truque, 1, 2, …" with the UI in English. This is derived app vocabulary keyed off a
canonical literal — the exact category D-02 says follows `uiLang` "sempre" — and plan 05
translated its two siblings (school, conc/rit yes-no) while leaving this one. The
literal predates the phase, but D-02 put it in scope and the desktop/mobile divergence
proves the sweep was incomplete.

**Fix:**

```jsx
// v10-hifi.jsx:1263
{ key: 'level', label: tt(lang, 'spell.level'),
  values: hifiFilterValues('level', allSpells, versionLang),
  formatValue: v => (v === 'truque' ? tt(uiLang, 'spell.cantrip') : v) },
```

Better: hoist that ternary into a `hifiLevelFilterLabel(v, uiLang)` next to
`hifiSchoolFilterLabel`/`hifiClassFilterLabel` and call it from both screens, so the
three base filters share one shape. Then extend
`scripts/check-filter-lang-vocabulary.tests.ps1` to require it at both call sites,
matching what it already does for school and class.

### WR-04: Plain-text fallback branches of pack content have no `lang` attribute (WCAG 3.1.2)

**File:** `v10-hifi.jsx:678`, `v10-hifi.jsx:1017`, `v10-hifi.jsx:1026`, `v10-hifi.jsx:353`, `v10-hifi.jsx:359`

**Issue:** Every description/upgrade render site is a ternary. The `descHtml` branch got
`lang={hifiHtmlLang(versionLang)}`; the plain-text `<p>` / bare-string branch did not:

```jsx
{descHtml
  ? <div className="hifi-rich" lang={hifiHtmlLang(versionLang)} dangerouslySetInnerHTML={...}/>
  : <p style={{ margin: 0, textWrap: 'pretty' }}>{desc}</p>}   // ← unmarked
```

The same text, from the same pack, in the same language, is marked in one branch and
unmarked in the other. The unmarked branch is reachable: `descHtml` is `''` for any pack
whose descriptions are plain text, which is a first-class case under BYOD. D-05 enumerated
"os 5 sinks" and the implementation followed the enumeration literally rather than the
rule it encodes.

The same omission covers the other pack-owned strings rendered as chrome-adjacent values:
`HifiStat` values `s.time`/`s.range`/`s.dur`/`s.comp` (`:1006-1009`), the card footer's
`s.range` and `s.src` (`:697`, `:700`), and the print sheet's `<dd>` values (`:337-340`) —
all raw pack text (D-03 keeps them in `versionLang`) inside a `uiLang` document.

**Fix:** move the attribute up to the branch-independent container so both branches inherit
it, which also shrinks the diff:

```jsx
<div className="hifi-card-desc" lang={hifiHtmlLang(versionLang)} style={{...}}>
  {descHtml ? <div className="hifi-rich" dangerouslySetInnerHTML={...}/> : <p>{desc}</p>}
</div>
```

Apply the same container-level marking to the detail-panel description/upgrade blocks
(`:1013-1027`), the stats grid (`:1005-1010`), and the print card body. Then relax the
`check-content-lang-ownership.tests.ps1` sink assertion from "same line" to "sink or its
container", so the test does not force the attribute back down onto the sink element.

### WR-05: Character editor spell name follows the pack but is not marked with the pack's language

**File:** `v11-character-editor.jsx:957`

**Issue:** Plan 03 correctly switched the editor's spell name to `spellName(s, versionLang)`,
which means a Portuguese-UI user browsing an EN pack now sees English spell names in the
editor's spell list. D-05 names "o nome da magia" as one of the six content regions that
must carry its own `lang` — the editor was the one mount point that got the `versionLang`
half of the change without the `lang` half. Screen readers will pronounce English spell
names with Portuguese phonemes.

**Fix:**

```jsx
<div lang={window.hifiHtmlLang ? window.hifiHtmlLang(versionLang) : (versionLang === 'ptbr' ? 'pt-br' : 'en')}
     style={{ fontFamily: "'Texturina', ...", fontWeight: 600, fontSize: 14, color: 'var(--text)' }}>
  {spellName(s, versionLang)}
</div>
```

`hifiHtmlLang` currently lives in `v10-hifi.jsx`, which loads *after*
`v11-character-editor.jsx`; export it on `window` from `v10-hifi.jsx` (it is only read at
render time, so load order is not a problem) rather than duplicating the ternary. Add the
assertion to `scripts/check-editor-version-lang.tests.ps1`, which today checks the
`versionLang` half only.

### WR-06: The signature split was applied to three functions that have no callers, and a test now pins dead code

**File:** `v10-hifi.jsx:121` (`hifiShare`), `v10-hifi.jsx:138` (`hifiPrint`), `v10-hifi.jsx:143` (`hifiPrintList`), `scripts/check-content-lang-ownership.tests.ps1:73`

**Issue:** `hifiShare`, `hifiPrint` and `hifiPrintList` have zero call sites anywhere in
the repo — verified across `*.jsx`, `*.html` and `*.js`, and verified dead at `8a9b5a2`
too, so the phase did not orphan them. The phase nonetheless rewrote all three
signatures, and `check-content-lang-ownership.tests.ps1:73` now asserts
`function hifiShare(s, uiLang, versionLang, show)` — the test's own comment concedes
this is "a unica forma estatica de pegar referencia a variavel nao declarada num helper
sem chamador". That is a test whose only purpose is to keep dead code internally
consistent.

The same phase ran a "Dead Code Ledger" that correctly killed `remapClassFilter` and the
`lang` parameter of `buildSpellLink`. These three should have been in the same ledger.

**Fix:** delete `hifiShare`, `hifiPrint` and `hifiPrintList` (`v10-hifi.jsx:118-146`,
keeping `hifiPrintPrepared`, which is live), drop assertion 7 from
`check-content-lang-ownership.tests.ps1`, and drop the now-unreachable legacy-`lang`
fallback in `HifiPrintRoot` (see IN-04). If the print-single-spell button is planned for
a later phase, re-add the helper then — with a caller.

### WR-07: The same class values render in two different languages on the same screen

**File:** `v10-hifi.jsx:1031-1035` (detail panel), vs `v10-hifi.jsx:1265` / `:2498` (filter chips)

**Issue:** D-04 made the class *filter label* follow `uiLang`
(`hifiClassFilterLabel(v, uiLang)`), while the detail panel's Classes list still renders
`s.classes` raw:

```jsx
{(s.classes || []).map(c => c ? c.charAt(0).toUpperCase() + c.slice(1) : c).join(', ')}
```

With a PT interface on an EN pack, the filter chip offers "Mago" and the detail panel for
the spell you just filtered says "Wizard". Same datum, same screen, two languages, and the
detail-panel copy carries no `lang` attribute either. D-03 (values stay `versionLang`) and
D-04 (labels follow `uiLang`) are both satisfied in isolation — the inconsistency is
between them, and the user sees it.

**Fix:** reuse the helper the phase just added, so both surfaces speak the interface
language:

```jsx
{(s.classes || []).map(c => hifiClassFilterLabel(c, lang)).join(', ')}
```

`hifiClassFilterLabel` already does the title-casing, so this is a net simplification.
If the class list is instead deemed pack content, mark the `<p>` with
`lang={hifiHtmlLang(versionLang)}` and leave it raw — but pick one, and state which in
the decision record.

### IN-02: `const uiLang = lang;` alias produces a duplicated dependency

**File:** `v10-hifi.jsx:1124`, `v10-hifi.jsx:2169`, `v10-hifi.jsx:1266`

**Issue:** The alias is documented as a readability aid, but the result is two names for
one value used interchangeably inside the same expression — `filterCats` reads
`tt(lang, 'spell.school')` and `hifiSchoolFilterLabel(v, uiLang)` on adjacent lines — and

(`function HifiDesktop({ uiLang: lang = 'ptbr', ... })` is not it — rename the prop to

### IN-03: `normLang ? normLang(v) : v` is not a working guard

**File:** `index.html:517`

**Issue:** If `normLang` were genuinely absent, the bare identifier reference throws
`ReferenceError` before the ternary can evaluate — the guard cannot fire. It only works
for the case where `normLang` is declared and falsy, which cannot happen (it is a
function declaration in `i18n.jsx:364` plus `window.normLang` at `:437`).

**Fix:** `window.__setUiLang = (v) => setUiLang(window.normLang ? window.normLang(v) : v);`
— property access is safe on a missing global, and it matches how the rest of
`v10-hifi.jsx` reaches loader globals. Update the matching assertion in
`check-ui-lang-state.tests.ps1:22`.

### IN-04: `HifiPrintRoot`'s legacy `lang` fallback is unreachable, and its two defaults disagree

**File:** `v10-hifi.jsx:185-187`

**Issue:** The fallback exists for "um `detail` antigo (chave única `lang`, listener é
global e o evento é público)". No dispatcher in the repo emits the single-key shape —
the only live dispatcher, `hifiPrintPrepared`, always sends both keys, and the other two
dispatchers are dead (WR-06). Worse, if both keys were ever missing the two halves
disagree: `tt(undefined, ...)` resolves to Portuguese via `normLang`, while
`hifiHtmlLang(undefined)` returns `'en'` — Portuguese chrome inside `lang="en"`, the same
class of defect as WR-02.

**Fix:** delete the `legacyLang` destructure and the two `||` fallbacks together with
WR-06's dead dispatchers. If the fallback is kept, make it explicit and consistent:
`const uiLang = normLang(uiLangIn || legacyLang);`.

### IN-05: `hifiClassFilterLabel` reintroduces a prototype-bearing dictionary in the exact function that later calls `.charAt()`

**File:** `v10-hifi.jsx:804`

**Issue:**

```js
const dict = uiLang === 'ptbr' ? (window.CLASS_PT || {}) : (window.CLASS_EN || {});
const translated = dict[String(value || '').toLowerCase()] || value;
return hifiTitleCaseFilterLabel(translated);   // → .charAt(0) on the result
```

`CLASS_PT`/`CLASS_EN` are `Object.create(null)` specifically because "adaptSpell() indexa
esta tabela com strings vindas direto do JSON de um pack de terceiro… a chave
'constructor' devolveria a funcao herdada — truthy, entao o fallback `|| c` nao salvaria,
e ela chegaria ate .charAt() na tela de detalhe" (`spells-data-loader.jsx:224-225`). The
`|| {}` fallback is a plain object literal, so the new helper is the precise shape CR-03
was filed against. Only reachable if the loader script failed to execute, in which case
there are no spells to filter — hence Info, not Warning.

**Fix:** `const EMPTY = Object.create(null);` at module scope and use it as the fallback,
or drop the `||` entirely and let a missing global surface as an error.

### IN-06: I18N-01 is implemented but left unchecked in REQUIREMENTS.md

**File:** `.planning/REQUIREMENTS.md` §I18N (tracking artifact, not source)

**Issue:** I18N-02 and I18N-03 are `[x]`; I18N-01 ("idioma da interface é estado próprio,
persistido em `spellbook-ui-prefs`, independente da versão ativa") is still `[ ]` even
though plan 01 delivered it and `check-ui-lang-state.tests.ps1` guards it.
`04.1-05-SUMMARY.md` records the omission and declares the fix out of scope. The phase
therefore closes with a delivered requirement reading as incomplete, and the traceability
table at the bottom of REQUIREMENTS.md has no I18N rows at all.

**Fix:** tick I18N-01 and add the three I18N rows to the traceability table before the
phase is marked done.

### IN-07: `hifiFilterConfig('en')` is called per URL parameter purely to test key membership

**File:** `v10-hifi.jsx:834`

**Issue:** `if (!Object.prototype.hasOwnProperty.call(hifiFilterConfig('en'), k)) return;`
builds a full config object (11 entries, 11 `tt()` lookups) inside a `p.forEach` loop, and
hardcodes `'en'` — which was already language-irrelevant before this phase and is now
provably so, since `get`/`values` no longer read `lang` at all. The hardcoded language
also makes the call read like a bug to the next reader.

**Fix:** hoist the key set to module scope, which drops the loop allocation and the
misleading argument in one line:

```js
const HIFI_FILTER_KEYS = new Set(Object.keys(hifiFilterConfig('en')));
```

Guard it behind the existing `['class','level','school'].includes(k)` check that follows,
or replace both checks with the explicit whitelist, which is what the IN-06 comment right
below it says is the real contract.

## Resolução do CR-01 (orquestrador, 2026-08-24)
